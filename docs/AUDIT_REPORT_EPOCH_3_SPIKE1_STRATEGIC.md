## 1. Ответ на вопрос Гриши: A, B или C?

**Критически важная оговорка до выбора.** По вашим же фактам `socketFactory` вызывается **синхронно**: `this.options.socketFactory?.(wsUrl) ?? new WebSocket(wsUrl)` (`json-rpc-gateway.ts:241`, `WS_DIAL_WIRE`). Значит, фабрика должна вернуть WebSocket-подобный объект **сразу**, а потом вызвать `onopen`. Ваш `window.__POSEIDON_SOCKET_FACTORY__ = () => PoseidonGatewaySocket.connect()` возвращает **Promise** (`static async connect`). Присвоение `promise.onopen = …` ничего не делает. Даже если хук в апстриме найдётся, UI останется на «Starting Hermes…». Это нужно исправить при любом из трёх вариантов.

| Вариант | Мой вердикт | Почему |
|---|---|---|
| **A** (патч `openGatewaySocket`) | 🟡 запасной | Минимален, но это правка файла, которого мы не контролируем, с мержем после каждой синхронизации. |
| **B** (Vite alias / shim-модуль) | ❌ | Работает только там, где вы запускаете **их** Vite-конфиг (dev). Для production-сборки (`apps/desktop` dist, который вы планируете монтировать как `frontendDist`) алиас не сработает. |
| **C** (свой тонкий чат) | ❌ | Это второй UI, который придётся поддерживать, и прямое противоречие ADR-014 и цели Spike 1. Годится только как диагностический стенд, не как решение. |
| **D** (моя рекомендация) | ✅ | **Шим глобального `WebSocket`** в `initialization_script`. |

**Почему D.** Апстримный `openGatewaySocket` в конце концов делает `new WebSocket(url, [protocols])`, а `WebSocket` разрешается как глобал **в момент вызова**. Если наш скрипт выполнился раньше кода страницы, подмена видна без единой правки апстрима, и для dev (Vite), и для prod (dist). Для URL не-шлюза (HMR Vite: `ws://127.0.0.1:5174/` с протоколом `vite-hmr`) шим пропускает вызов в нативный `WebSocket`.

**Как это сделать:**
1. `PoseidonWebSocket(url, protocols)` — **синхронный** конструктор: `readyState = CONNECTING`, свой `id`, `invoke('gateway_ws_open', {id, url, protocols})` в фоне, потом `onopen`/событие `open`.
2. API как у браузера: `addEventListener/removeEventListener`, `onopen/onmessage/onerror/onclose`, `close(code, reason)`, `send`, `url`, `protocol`, `binaryType`, `bufferedAmount`, константы. `onclose` получает `{code, reason, wasClean}` (апстрим, вероятно, читает `code`: `[НЕ ПРОВЕРЕНО]`).
3. **Rust получает URL и протоколы от рендерера**, проверяет их и дозванивается именно по ним (без повторного `ensure` и минта): хост только loopback, порт и origin совпадают с endpoint из `ensure`, путь строго `/api/ws`, протоколы из allowlist (`hermes-gateway-v1`, `hermes-gateway-ticket.*`). Тогда работает апстримная логика повторных попыток (8×3 с, перевыпуск тикета перед каждой попыткой), а Rust не «знает» про тикеты больше необходимого.
4. События с `id`: `gateway-ws-frame {id, data}`, `gateway-ws-status {id, …}`, и `emit_to("main", …)` вместо широковещания.
5. Если в будущем Nous согласится принять маленький хук («инъектируемый транспорт» или capability), шим заменяется на вариант A **с поддержкой апстрима**. Эту просьбу стоит включить в письмо Nous (§6).

Все пункты с API Tauri помечены `[ПРОВЕРИТЬ СБОРКОЙ]`.

## 2. Вероятные причины белого экрана (по убыванию правдоподобия)

Это не диагноз: я не вижу консоль. Но по коду причины видны.

### W1 🔴 Инъекция через `eval` слишком поздняя и хрупкая `[ПРОЧИТАНО]` + `[ПРОВЕРИТЬ СБОРКОЙ]`
`inject_bootstrap` вызывается из `setup` и ещё четыре раза по таймерам (300–3000 мс). React Hermes читает `window.hermesDesktop` при загрузке модулей. Если скрипт придёт позже, на старте будет `undefined`. А каждая перезагрузка страницы (в том числе Vite HMR full-reload) **обнуляет** инъекцию, и повторять её некому. Правильный примитив в Tauri 2: **`initialization_script`**, он выполняется **перед** скриптами страницы при каждой загрузке документа. Для окна из конфига: `"create": false` в `tauri.conf.json` и в `setup` создавать окно через `WebviewWindowBuilder::from_config(...)` с `.initialization_script(BOOTSTRAP_JS)`. Замечание в SPIKE1 «нет `WebviewWindow::on_page_load`» верно, но это не единственный путь: нужен именно `initialization_script`, а не `on_page_load` (он срабатывает на `Started`/`Finished`, а не гарантированно «до» кода страницы).

### W2 🔴 Две реализации моста, и в окно попадает худшая `[ПРОЧИТАНО]`
- Реально выполняется `src/desktop-bridge/poseidon-bootstrap.js` (его делает `include_str!`). В нём `stub()` возвращает **плоскую функцию**. Значит, `window.hermesDesktop.profile.getDefault()` даёт `TypeError: not a function`, а по вашим фактам именно это вызывается на шаге 3 загрузки (`desktop.profile.getDefault()/get()`, `use-gateway-boot.ts:760/787`).
- Правильный рекурсивный Proxy (`hermes-desktop-proxy.ts`) написан, но **никуда не собирается**: ни Vite, ни esbuild его не бандлят, `include_str!` берёт `.js`.
- Исправление: **один источник правды**. Писать на TS, собирать в IIFE (esbuild/Vite lib mode), `include_str!` брать из артефакта сборки. Дублей быть не должно.

### W3 🟠 Формы значений не сверены с апстримом `[ПРОЧИТАНО]` + `[НЕ ПРОВЕРЕНО]`
- `getConnection` возвращает ваш `ConnectionInfo` (`kind/state/apiOrigin/…`). По фактам Electron main отдаёт **дескриптор** вида `{wsUrl, authMode:'native', token:'', …}` (`local-gateway.ts:254`, `connection-config.ts`). Берите поля из типа в `connection-config.ts`, а не придумывайте.
- То же для `getBootProgress`: нужен апстримный тип, а не `{phase, ready, detail, percent}` по вашему вкусу. `getGatewayWsUrl` (`{ok, wsUrl}`) совпадает.

### W4 🟠 Синхронность фабрики сокета: см. §1.

### W5 🟠 `Origin` может мешать не только WebSocket `[НЕ ПРОВЕРЕНО]`
Electron main вычищает `Origin` только для `resourceType === 'webSocket'`. Что происходит с `fetch`/REST-вызовами рендерера к `api_origin` и с `getPluginWsUrl`, я не знаю. **Проинвентаризируйте все сетевые вызовы рендерера к шлюзу** (`grep` по `fetch(`, `new WebSocket`, `EventSource`, `getPluginWsUrl`). Если есть REST, ему нужен тот же Rust-транспорт (HTTP из Rust без браузерного `Origin`) или тот же шим.

### Как перестать гадать: boot-trace за один запуск
1. Сделайте рекурсивный Proxy единственным (W2).
2. Пусть каждое обращение (`path`, аргументы, результат/исключение) пишется через `append_ui_log` в `logs/poseidon-ui.log`.
3. Запустите Hermes UI. Результат: `docs/upstream/BOOT_TRACE.md` с **фактическим** минимумом ключей (то, что ваш `HERMES_FACTS` вывел только статикой, вариант B).
4. Параллельно: пусть Толян пришлёт **первую красную ошибку из DevTools Console** (одна строка). Это сэкономит часы.

## 3. Новые находки в коде

### 🔴 N1. WsBridge: исходящие сообщения ждут до 1 секунды `[ПРОЧИТАНО]`
В `ws_bridge.rs` у `TcpStream` стоит `read_timeout = 1 s`, а очередь исходящих (`rx.try_recv()`) проверяется только **в начале цикла**, до блокирующего `socket.read()`. В простое поток сидит в `read()` до секунды, поэтому **каждое сообщение пользователя и каждый heartbeat уходят с задержкой до ~1 с**. Для чата это заметно. Лечение: таймаут 20–50 мс, либо разделение чтения и записи (non-blocking + `mio`), либо `tokio-tungstenite` (рантайм Tauri у вас уже есть).

### 🔴 N2. Один сокет на процесс; новый `connect` убивает старый `[ПРОЧИТАНО]`
`WsBridge` держит одну сессию, а `connect()` начинает с `self.close()`. По вашим фактам рендерер знает несколько WS-путей (`getGatewayWsUrl`, `getGatewayWsUrlFor`, `getPluginWsUrl`, перепод­ключения). Второй вызов оборвёт первый. Нужны идентификаторы сессий (см. §1), карта сессий и события с `id`.

### 🟠 N3. `gateway_ws_connect` игнорирует URL рендерера и минтит заново `[ПРОЧИТАНО]`
Команда не принимает аргументов: внутри `mint_local_ws_url()` каждый раз запускает `hermes gateway ensure --json` (процесс Python) и минтит новый тикет. При повторных подключениях это дорого, а тикет, выданный рендереру через `getGatewayWsUrl`, оказывается ненужным. Фикс: дозваниваться по URL от рендерера после проверки (§1); `ensure` кэшировать (instance_id) с TTL и обновлять только при ошибке `stale runtime instance`.

### 🟠 N4. `ensure` без таймаута `[ПРОЧИТАНО]`
`Command::output()` без ограничения времени: если `hermes gateway ensure` зависнет, поток `spawn_blocking` повиснет навсегда. Нужны таймаут, отмена и ограничение числа одновременных `ensure` (single-flight). Состояние `!= "ready"` сейчас возвращается как ошибка без повтора. Апстрим делает 8 попыток по 3 с, поэтому повтор должен быть либо на стороне рендерера (оставив апстримную логику), либо в Rust.

### 🟠 N5. `GatewayManager` описывает не тот компонент, и модель владения устарела `[ПРОЧИТАНО]` + `[НЕ ПРОВЕРЕНО]`
- Ваши факты говорят, что `HERMES_BACKEND_READY port=N` печатает `hermes_cli/web_server.py` (веб-бэкенд/дашборд), а Desktop находит **шлюз** через `hermes gateway ensure --json` и control-socket. `GatewayManager` по-прежнему спавнит `hermes serve`, ждёт READY и по умолчанию смотрит порт 8642. То есть он управляет другим процессом, чем тот, с которым говорит чат.
- Шлюз на вашей машине управляется `supervisor: systemd`. Значит, жизненный цикл у него **не наш**. Мой R1/R5 (сироты, SIGKILL по группе) касались `hermes serve`; для нового пути они **почти не нужны**, пока оболочка ничего не спавнит сама.
- Предлагаю: либо **заморозить `gateway_start/stop`** (пометить `legacy`, убрать из bootstrap), либо переопределить их под `ensure`. Обновить ADR-009: «Poseidon не владеет шлюзом, владеет супервизор; убивать нечего». И один важный вопрос: **что делает `ensure`, если systemd нет** (macOS, контейнер, минимальный Linux)? Спавнит отвязанный процесс? Тогда кто его остановит и как мы это узнаем?
- Это же закрывает мой R3: ответы получены (ensure + control socket + singleton-lock, второй `gateway run` выходит с кодом 75). Спасибо, `HERMES_FACTS` отличный.

### 🟠 N6. Безопасность: рендерер получил управление агентом `[ПРОЧИТАНО]`
`get_gateway_ws_url` отдаёт рендереру URL с тикетом `scope: host`, `purpose: interactive`, а по вашим же фактам такой тикет даёт `session:create, session:submit, session:control, session:approve, session:respond`. Плюс `gateway_ws_send` пересылает любой кадр. Любой скрипт в WebView (например, XSS из вывода модели) может одобрить вызов инструмента на машине пользователя. В апстриме у рендерера то же право, но под `contextIsolation`/sandbox и строгим CSP. У вас: `csp: null` в `hermes-dev`, `unsafe-inline` + `withGlobalTauri: true` в основном конфиге, нет app manifest для своих команд (`build.rs` по-прежнему `tauri_build::build()`). **Не блокер Spike 1, блокер любого релиза.** Минимум: строгий CSP, `withGlobalTauri: false`, app manifest, allowlist назначений в Rust (§1), `emit_to` вместо `emit`.

### 🟡 N7. Прочее по коду
- **`uuid_v4_simple`** строится из наносекунд, это не случайное число. Для `native_dial` в Rust-пути nonce, видимо, не нужен совсем; если нужен, возьмите `getrandom`.
- **Состояние сессии**: поток чтения при завершении не очищает `tx`, поэтому `is_connected()` может врать после закрытия сервером.
- **`append_ui_log`** без лимита размера и ротации: рендерер может писать в файл бесконечно. Ограничьте размер, не логируйте URL и тикеты.
- **Windows**: весь путь подключения под `#[cfg(unix)]`. Зелёный CI на Windows означает только то, что заглушки компилируются. Это допустимо при явном решении «unix-first»; запишите его ADR-ом.
- **Лок-файлы**: `package-lock.json` убран из `.gitignore`, но в срезе его по-прежнему нет, `Cargo.lock` тоже. CI всё ещё на `npm install`.
- **Тесты**: 10 штук (3 + 5 + 2), на `WsBridge`, ticket-flow и ensure-парсер с живым выводом нет ни одного. Фикс R1 в `gateway.rs` есть, **теста на него нет** (фиктивный шлюз + `stop()` во время ожидания).

6. **N5**: заморозить `gateway_start/stop`, переписать ADR-009.
7. **Доказательство успеха Spike 1** в репозитории, а не в словах: `docs/reports/SPIKE1_RESULT.md` с (а) скриншотом окна, (б) транскриптом кадров `gateway-ws-frame` для одного сообщения туда и обратно, (в) логом. Критерий из вашего плана («чат открывается и говорит со шлюзом») считается выполненным, когда этот артефакт лежит в репо.

## 6. Стратегия: что Spike 1 уже дал для «душителя»

- Протокол теперь **описан**: `ensure` → control-socket `session-ticket` → WS `/api/ws` с `hermes-gateway-v1` → JSON-RPC (`gateway.ready`, `client.capabilities`, `gateway.ping`, `session.events.since`). Это основа для спецификации.
- **Первые куски на Rust уже есть**: клиент control-socket, парсер `ensure`, диалер WS. Запишите это ADR-ом как «первый перенесённый компонент» (клиентская сторона протокола): аудитория ADR-010 увидит, что «душитель» начался.
- Практичный следующий шаг: **писать `gateway-ws-frame` в файл** (флаг dev) и получить первые «золотые» транскрипты для харнесса паритета. Дёшево и сразу пригодится.
- **Письмо в Nous Research**: теперь есть конкретика. Что просить: (1) хук инъекции транспорта (`socketFactory`/capability) в рендерере, (2) стабильный документированный контракт `hermesDesktop` с версией, (3) подтверждение, что формат `ensure --json` и control-socket протокол считаются публичными. Это снимает необходимость и патча (вариант A), и шима.
